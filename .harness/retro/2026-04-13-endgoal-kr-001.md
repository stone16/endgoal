## Findings

### Proposal 1: Apply configured coverage gates during checkpoint evaluation

- **Pattern**: coverage-gate-drift
- **Classification**: skill defect
- **Severity**: high
- **Status**: Proposed
- **Root cause**: The spec required 95% line coverage per checkpoint and `.harness/config.json` set `coverage_threshold` to 95, but multiple checkpoint evaluations recorded coverage as unknown or not measured while still reaching PASS. Some evaluator artifacts also referenced the quick-reference 85% default rather than the task-specific 95% threshold. Full verification later found Rust workspace coverage at 86.61%, which required a late coverage-only commit to reach 95.01%.
- **Drafted rule text**:
  ```markdown
  When a harness spec or `.harness/config.json` defines a coverage threshold, checkpoint evaluators must apply that task-specific threshold. If coverage is an acceptance criterion, unknown or unmeasured coverage is a hard gate, not a PASS note. Missing coverage tooling should fail the checkpoint or full-verify phase unless the spec explicitly exempts that checkpoint type.
  ```
- **Issue-ready**: true

### Proposal 2: Make PR evidence reviewer-accessible when artifacts are local

- **Pattern**: local-artifact-evidence
- **Classification**: project workflow
- **Severity**: medium
- **Status**: Monitoring
- **Root cause**: The PR body summarized the passed commands and coverage, but also referenced `.harness/...` and `.review-loop/...` paths. Those directories are local/ignored harness artifacts and are not directly accessible from GitHub unless separately attached or committed. This did not block the run because the body included enough command-level evidence, but future PRs should avoid relying on local-only paths for reviewer evidence.
- **Drafted rule text**:
  ```markdown
  When a PR references harness evidence, summarize the relevant results directly in the PR body. Treat `.harness/` and `.review-loop/` paths as local execution artifacts unless they are intentionally committed or attached elsewhere.
  ```
- **Issue-ready**: false

### Proposal 3: Keep formatting scope explicit during late verification fixes

- **Pattern**: full-verify-formatting-churn
- **Classification**: project workflow
- **Severity**: low
- **Status**: Monitoring
- **Root cause**: The late coverage characterization commit included useful tests, but `cargo fmt --all` also normalized formatting in several surrounding files outside the direct test additions. The churn was safe and committed intentionally, but broad formatting in the final verification phase can make a large PR harder to review.
- **Drafted rule text**:
  ```markdown
  During late verification-only fixes, prefer formatting the files touched by the fix. If running a whole-workspace formatter, call out the formatting scope in the commit or PR summary.
  ```
- **Issue-ready**: false
